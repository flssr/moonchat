# 消息与会话

消息读写都走客户端的 Turms 会话。Web 端通过 `dart:js_interop` 调用仓库内置的 `turms-client-js`；Windows 桌面端在 `desktop/lib/realtime.dart` 里按同一线上格式直连 `/im` WebSocket（一帧一个 protobuf，按 `requestId` 配对）。Turms 官方的 Dart 客户端只支持 TCP 11510，部署只暴露 10510 的 WebSocket，所以桌面端不复用它。

## 会话与历史

- 私聊 key 是 `dm:<peerAccountId>`，群聊 key 是 `room:<roomId>`。
- 客户端监听该账号全部新消息，并接受同一消息的推送去重；本地「发送中」气泡只认领 `senderId` 是当前账号的回声，对端发来的同文本消息正常插入，避免双方同发一句话时吞消息。
- 会话行显示最后一句话（超长省略），收到非当前会话的消息累加未读角标；打开会话后经 Turms 上报已读，上报成功后本地角标清零。窗口在前台且正看着该会话时不累计未读。
- 未读基线：私聊用**本机已读时间**（随 `cache.json` 落盘，键是会话 key）；群用 Turms 的 `memberIdToReadDate[自己]`。`deliveryDate` 晚于基线、不是自己发、未删除的消息算未读。私聊查不到自己的服务端读时间：`QUERY_CONVERSATIONS_REQUEST` 的 `userIds` 在服务端是 owner，返回的是「对方对我的会话」，`readDate` 是对方的（[#37](https://github.com/flssr/moonchat/issues/37)）；不要拿它当基线。群的整张成员已读表只用自己那条，不显示谁读过。
- 上报走 `updateConversationRequest`（私聊目标账号、群 `groupId`；`readDate` 省略，由服务端取当前时间）：打开会话、窗口回到前台、正看着会话收到新消息各触发一次，同一会话 1 秒去抖；失败（群关闭已读 `4000/4001`、时间回拨 `4004` 等）静默跳过。上报成功后本机读时间立刻前进并落盘（私聊未读就靠它）。查历史不会自动推进已读。Web 端的 `turms-client-js` 生成模型把私聊字段叫 `targetId`（proto 的 `target_id`），会话服务封装仍写 `userId`，那个字段会被编码器忽略并回 `1102`——客户端直接按模型字段发请求，不改 vendor。
- 本机没有任何已读基线的会话（首登/重装），首次补拉时静默上报一次已读（避免历史消息一登录全红），并把时间写进本机基线；之后按本机基线算。
- 收到消息时，如果窗口不在前台或不是当前会话，按设置弹桌面通知（Windows `local_notifier`）；设置里可选「收到消息并且提示 / 不提示」。
- Windows 桌面端把每个会话最后 200 条和当前会话同步缓存到本机 `MondChat\cache.json`（按账号分）；存储根目录依次取 `APPDATA`、`LOCALAPPDATA`、用户 Roaming、exe 同目录里第一个可写的，避免某些启动方式下 `%APPDATA%` 为空导致整机不落盘。重登先用缓存铺回会话列表与上次聊天，再由 Turms 历史/推送覆盖。Web 不落盘。
- 登录/恢复会话后对每个会话补拉最新一页：填会话列表预览，并把基线之后的对端消息计为未读、按设置弹桌面通知（正文带条数和最后一条内容）；即使恢复的当前会话就是它也要提示。历史回填本身不触发未读，只有实时推送和登录补拉算“收到”。基线见上（私聊本机、群 Turms）；没有基线的会话静默上报一次，不把历史全算成未读。之后只在「打开会话且未读 > 0」「窗口回到前台且未读 > 0」或「正看着会话收到新消息」时上报，1 秒 debounce。
- 会话列表按最后一条消息时间倒序，新消息会话排到最前；单会话未读显示在行尾（99+ 上限），导航栏“消息”图标显示总未读。
- 桌面端 Turms 通道发心跳（30 秒空闲一次），90 秒收不到任何回包就判半开连接；断开后指数退避自动重连，重连成功补拉当前会话最新一页，断线期间漏掉的推送从历史补齐。Web 端没有自己的重连：断开后状态层按 1/2/4/8/16/30 秒换凭据重连，成功后同样补拉当前会话。
- 群推送带 Turms `groupId`，客户端先按 `GET /api/rooms` 返回的 `turms_group_id` 映射回业务群，再更新会话。
- 历史用 `deliveryDate` 与 `descending` 往回翻，游标取当前最早消息的时间；不能用消息 id 翻页。

## 渲染

消息按发送者与时间分组后再进列表：同一人、五分钟内、同一天的消息算一组，头像只在组首出现，时间与发送状态挂在组尾，跨天插一条细线日期。群聊用成员资料里的名字与头像；成员还没加载时退回账号 id 与首字头像。气泡与列表的视觉规则见 [design.md](./design.md)。

## 发送

发送走已有的 Turms WebSocket：Web 调 `messageService.sendMessage({isGroupMessage, targetId, text})`，桌面端按同一帧格式直接发 `createMessageRequest`。`dm` 的 `targetId` 是对端账号 id、群聊是 `turms_group_id`；不传 `messageId` / `deliveryDate`，由服务端生成。气泡仍是本地占位，直写响应给的 `messageId` 先落定，收到通知里的同一个 id 只做去重与时间校正。没有 Biz 回执，也没有经 Biz 的兜底路径。

直写需要服务端打开 `MONDCHAT_TURMS_WRITE_CREDENTIAL_ENABLED=true`，给客户端凭据签 `MESSAGE.CREATE` / `MESSAGE.UPDATE` / `CONVERSATION.UPDATE`；开关未开时直写回 `1106`，这是预期的中间态。

输入框里 Enter 直接发送，Shift+Enter 换行；输入法还在组词时的 Enter 交给候选上屏，不发出去。

本人 5 分钟内的已发送消息可以从组尾的「撤回」或右键/长按气泡撤回，请求是 `updateMessageRequest`（Web 由 `turms-client-js` 补当前时间，桌面端显式带本地当前时间）。成功后本地立即显示「已撤回」，其他端靠更新通知标记；失败按 `5200/5201/5202/5204` 分流。历史重拉后服务端默认不返回已撤回消息。

错误一律按 Turms 的 `code` 分流，不看 HTTP 状态（`4000/4001/4004/5007/5201` 的状态是 510）：非好友 `5001`、被拉黑 `5002`（`stranger=false` 时压成 `5001`）、群不允许游客发言或游客被禁言 `5009`（文案不能写成「你不是群成员」）、群或成员被禁言 `5005/5008`、群不可用 `5004/5006`、给自己发消息 `5007`、敏感词 `5010`、撤回失败 `5200/5201/5202/5204`、无写权限含冻结 `1106`、限流 `1101`（保留草稿，退避重试）。`1105` / `1300` 触发换 Turms 凭据重连。

没有已读回执给他人、正在输入、消息搜索、附件、音视频或结构化 mentions；读游标只用于自己的未读基线。
