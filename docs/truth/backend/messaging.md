# 消息与写入网关

消息只在 Turms。Biz 不保存消息、不参与投递、不订阅消息事件。

## 写入

唯一服务端写入口是 `POST /api/conversations/{type}/{id}/messages`。`dm` 的 id 是对端账号 id，`room` 的 id 是业务群 id。

固定校验顺序：

1. 认证凭据。
2. 归属与来源。
3. 会话解析。
4. PG 授权：群成员、好友、对端是否拉黑当前账号。
5. agent 两级限流。
6. 来源与限流日志。
7. `im-facade` 代发。

消息 id 由 Biz 生成；Turms Admin 不返回消息 id，也没有每会话序号。客户端历史分页使用 Turms 的 `deliveryDate`，不能用消息 id 当游标。

`X-Device-Type` 由客户端声明并映射到 Turms 枚举，不参与授权。正文上限 500 字符，`@` 只是正文。

## 已读上报

读游标由 Biz 代写：`POST /api/conversations/{type}/{id}/read`，无请求体，成功 `204`、无响应体。`204` 表示「已读到服务端此刻」，客户端收到即可在本地把该会话未读清零，不必再查一次 Turms 确认。

- `type` 与 `id` 的解析与发言相同：`dm` 的 id 是对端账号 id，`room` 的 id 是业务群 id。
- `dm` 只校验对端账号存在（404）且不是自己（400），不查好友关系——删好友后会话仍要能清角标。
- `room` 校验当前账号在 `room_member` 中（403），键用 `room_info.turms_group_id`，不是 PG 的 `room_info.id`；该列为空时与发言同口径 `503 upstream_unavailable`。
- `readDate` 一律传 `null`，由 Turms 取服务器时间。私聊只前进，群侧覆盖成新的「现在」，重复调用无副作用。
- 写的是调用者自己的读游标，不产生对他人的可见状态，也不改业务真相：冻结账号照样可以上报（不属于「停止写入」），也不进 agent 或账号限流桶。
- 写已读走 Turms Admin 的 `PUT /conversations`，不发通知；跨端是**被动**收敛，各端下一次查询会话时读到新的读时间，不做实时推送。
- Biz 不提供未读数接口；未读由客户端按 `readDate` 与本地历史计算。

### 客户端基线

「是否首次上报」由客户端本地判定，服务端不存这个状态。首次登录时对已有会话逐个静默上报一次（一次性 N 次 Admin 写，接受），之后只在「打开会话且未读 > 0」时上报，配 1 秒 debounce，登录时不再批量。不这样做，首登的历史会话都没有 `readDate`，会一次性全红。

### 已知上限

`/read` 不校验关系，任意「对端账号存在」的 `dm` 都会让 Turms upsert 出一条会话文档。客户端按显式 id 列表查私聊会话，这类孤立文档不会进入会话列表，代价只是存储。

## agent

agent 用账号密钥换 Turms 凭据，收该账号全部会话并自己筛选。平台没有 webhook、工作区、推送档位或专用 agent 接口。

agent 来源进账号级与会话级 Redis 桶，当前暂定 60 次/分钟与 20 次/分钟；归属者切进同一 agent 账号时来源是 `owner`，不进 agent 桶。限流先于代发，命中只写日志。

## 失败语义

成功 201 表示 Turms 已落库并接下投递，不表示对端已读。503 表示 Biz 没拿到 Turms 确认，Turms 可能已经落库；当前不做幂等，重试可能重复。

OneBot 11 只在 agent 侧桥接，平台不提供 `/onebot` 协议面。参考实现尚未开始。
