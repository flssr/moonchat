### 删好友保留私聊与删除并拉黑

2026-11-17 01:12 CET   [2026-11-17 00:12 UTC]

决策：删除好友不再清掉历史私聊：会话列表用本地消息把非好友的 DM 补回来，标题取之前缓存的好友名；双方再发送时客户端提示「当前不是对方好友，请添加后再进行会话」，不进入发送请求。删除确认里增加「删除并拉黑」，复用 `/api/blocklist`，被拉黑方无法再主动加回来。

原因：被删方不会收到删除通知，会话不能凭空消失；后端私有消息本来就拒绝非好友，客户端先给出可读提示；拉黑复用已有后端接口，不改消息写入边界。

### 同文本消息的本地回声认领

2026-11-16 20:55 CET   [2026-11-16 19:55 UTC]

决策：Turms 推回来的消息只有 `senderId` 是当前账号时才去认领本地「发送中」气泡；对端发来的消息即使是同一句文本也直接插入。

原因：双方同时发 666 时，接收端按文本认领会把对端那条吞进自己的待发气泡，两边列表对不上，看起来像“对面发了但我这边没有”。双端 120 条重复文本、短间隔、突发压力验证两端列表各 120 条、自己/对端各 60 条，无重复无缺失。

### 桌面端读通道断线自愈

2026-11-16 19:27 CET   [2026-11-16 18:27 UTC]

决策：桌面端 WebSocket 每 30 秒空闲发一次心跳，90 秒没有收到任何回包（包括心跳空帧）就判半开连接；断开后按 2/4/8/16/30 秒退避自动重连，重连成功补拉当前会话最新一页。显式登出或切号才停止。

原因：两个客户端同时在线、挂机久了会出现半开连接或会话被关，UI 仍显示“实时”，新消息不再到达；Turms 不会给断线期间的会话补推，只能靠重连后的历史查询补回来。只加重连不补历史，用户仍会看到“对面发了我却没收到”。

### 桌面端 Turms 传输

2026-11-16 17:16 CET   [2026-11-16 16:16 UTC]

决策：Windows 客户端不复用官方的 `turms-client-dart`（它只实现 TCP 11510），而是在 `desktop/lib/realtime.dart` 里按 `turms-client-js` 的线上格式直连 `/im`（10510）：一帧一个 protobuf，请求/响应按 `requestId` 配对，空帧做心跳，用 `DeviceType.DESKTOP` 登录。读通道只做登录、查历史与收推送，写仍然只走 Biz。

原因：生产与本地编排只把 Turms 的 WebSocket 端口暴露给反代（`/im`），TCP 11510 不出容器网络；为桌面端单独开 TCP 端口要动反代与 TLS，成本与风险都高于在客户端补一层已经固定的线上协议。proto 类直接依赖仓库固定提交里的 `turms-client-dart`，字段编号不手写。

### 输入框回车

2026-11-15 13:13 CET   [2026-11-15 12:13 UTC]

决策：Enter 发送、Shift+Enter 换行；输入法组词中的 Enter 不拦截，留给候选上屏。

原因：多行输入框默认把 Enter 当换行。在按键阶段吃下这个事件还能让 Web 引擎阻止浏览器把换行插进输入元素；组词中拦截则会把半截中文当成消息发出去（issue #24）。

### 群 id 映射

2026-11-11 20:34 CET   [2026-11-11 19:34 UTC]

决策：客户端按 `turms_group_id` 识别群推送和历史，再映射回业务 `roomId`。

原因：Turms 推送使用自己的群 id；不做映射会把群消息落到错误会话。

### 历史分页

2026-11-10 22:32 CET   [2026-11-10 21:32 UTC]

决策：历史使用 `deliveryDate` 往回翻，下一页游标取当前最早一条减一毫秒。

原因：Turms 不提供每会话序号或消息 id 范围分页；闭区间边界需要排除重复消息。

### 实时读取

2026-11-10 22:10 CET   [2026-11-10 21:10 UTC]

决策：Web 端通过 `dart:js_interop` 使用仓库内置的 `turms-client-js` 收推送和查历史。

原因：官方 Dart 客户端使用 TCP，浏览器不可用；固定子模块构建的 JS 客户端与服务端 proto 对齐。
