# biz 数据模型与表结构（DDD）

**一句话**：`moonchat-biz` 的 PostgreSQL 只有七张表——账号与统一认证信息、好友正反表、群信息与群成员正反表；消息与投递状态都不在这里。

## 0. 这份文档管什么

| 本文管 | 本文不管 |
| --- | --- |
| 表、列、类型、约束、索引、迁移文件形态 | 接口契约（`moonchat-api`）、V1 范围与验收（`moonchat-product`） |
| 聚合边界与聚合根 | Turms 里投影哪些字段（`moonchat-messaging`） |
| 哪些规则只能由应用层守 | 写入网关的校验顺序与限流速率（`moonchat-agent-connection`） |

- **本文不新增业务规则**，只把已定稿的 spec 里写下的业务真相落成结构。与 module spec 冲突时以 module spec 为准，并当场修本文。
- 判断标准只有一条：**表里的每一列都应该能指回某份 spec 的一句话**；指不回去的列，要么删掉，要么先在 spec 里补上它。

## 1. 限界上下文与聚合

| 上下文 | 聚合根 | 聚合内与关联 | 表 | 依据 |
| --- | --- | --- | --- | --- |
| 身份 | `Account` | `account` 保存身份与归属，`account_info` 保存名字、状态与唯一认证哈希（1 : 1） | `account`、`account_info` | `moonchat-accounts` |
| 关系 | `Friendship` | 申请与成立是同一行的两个状态；反向表是同事务维护的查询镜像 | `friendship`、`friendship_reverse` | `moonchat-friends` |
| 群 | `Room` | `RoomInfo` 与成员集合属于同一聚合；成员反向表是同事务维护的查询镜像 | `room_info`、`room_member`、`account_room` | `moonchat-messaging` |

三条聚合纪律：

- **一个事务只改一个聚合**。「注册或建 agent」在同一事务写 `account` 与 `account_info`；「退群」在同一事务改 `Room` 聚合的成员正反两张表；「删好友」在同一事务改 `Friendship` 聚合的两张表。跨聚合的一致性靠业务规则，不靠级联写。
- **`account.id` 是全库唯一的身份标识**，也是 Turms 用户 id；其余表对账号的引用一律是这一列，没有第二套 id。
- **投影状态不是业务状态**：`turms_sync_state` 只记录「PG 这一行有没有同步进 Turms」，不参与任何业务判定。

## 2. 表总览

| 表 | 一行是什么 | 基数 | 写入者 |
| --- | --- | --- | --- |
| `account` | 一个账号（human 或 agent） | 账号数 | 注册、建 agent |
| `account_info` | 一个账号的名字、状态、登录标识与唯一认证哈希 | 1 : 1 | 注册、建 agent、改名、冻结 |
| `friendship` | 一对账号之间的好友关系 | 无向、成对唯一 | 申请、同意、删除 |
| `friendship_reverse` | 同一好友关系按较大账号 id 反向存放的查询镜像 | 与 `friendship` 1 : 1 | 随 `friendship` 同事务写入、更新、删除 |
| `room_info` | 一个群（名称、群主） | 群数 | 建群、改名 |
| `room_member` | 一个账号在一个群里 | `(room, account)` 唯一 | 建群、拉人、退群、移除 |
| `account_room` | 同一群成员关系按账号 id 反向存放的查询镜像 | 与 `room_member` 1 : 1 | 随 `room_member` 同事务写入、删除 |

行生命周期（V1 不删账号，也不解散群）：

| 表 | 减行时机 |
| --- | --- |
| `friendship`、`friendship_reverse` | 拒绝申请、删好友 → 同事务写 `deleted_at`；超过保留期后由 Biz purge 物理删行 |
| `room_member`、`account_room` | 退群、被移除 → 同事务写 `deleted_at`；超过保留期后由 Biz purge 物理删行 |
| `account`、`account_info`、`room_info` | V1 不减行 |

## 3. 迁移与命名约定

- 迁移用 **Flyway**：路径 `moonchat-biz/src/main/resources/db/migration/`，第一个文件 `V1__biz_schema.sql`。实现时 `moonchat-biz/pom.xml` 需要补 `flyway-core`、`flyway-database-postgresql` 与 `org.postgresql:postgresql`（本文不改 pom）。
- 表名**单数 snake_case、不加前缀**（单库单域，七张表全部属于 biz）：`account`、`account_info`、`friendship`、`friendship_reverse`、`room_info`、`room_member`、`account_room`。
- 枚举用 **`text` + `check`**，不用 PG 原生 enum 类型：加一个取值是一条 check 迁移，不必改类型、不锁表。
- 时间列一律 `timestamptz`（UTC）；`updated_at` 由应用写，**不建触发器**。
- **所有外键都是逻辑外键**：DDL 不写 `references` / `on delete cascade`；写入时由应用层校验引用目标存在，删除父行时由同一事务处理不再需要的子行。
- 约束与索引命名：`表_pk`、`表_列_uq`、`表_列_idx`、`表_列_chk`；逻辑外键不是数据库约束，不生成 `_fk` 名称。
- `deleted_at` 只用于好友与群成员，表达可恢复的 tombstone；账号、资料与群信息都不做软删除（V1 没有删账号，也没有解散群）。不建 `version`、`created_by` / `updated_by` 这类通用列。

五条贯穿全部表的决定：

- **身份与资料认证分表**：`account` 只保存身份、类型和归属；人类与 agent 各有一条 `account_info` 保存名字、状态和认证信息。`account_info` 通过 `account_id` 与身份一一对应，认证算法由 `account.type` 决定。
- **软删后定期 purge**：删好友、退群、被移除先写 `deleted_at`，所有业务查询排除 tombstone；超过保留期后由 Biz 定期物理删除。保留时长与 purge 频率**未确认**。
- **主从镜像而不是双真相**：`friendship`、`room_member` 分别保存好友与群成员的权威值；`friendship_reverse`、`account_room` 只是为了按另一侧直接查询，必须在同一事务中镜像主表，且不参与授权判断。
- **没有多租户列**：单实例单库，不加 `tenant_id`。
- **id 类型统一 `bigint`**：`account.id` 必须是 Turms 的 Long 用户 id，其余 id 跟着统一，省掉「这个 id 是 uuid 还是数字」的分支。

## 4. DDL

下面七个小节每节只定义一张表，并按依赖顺序拼成 `V1__biz_schema.sql`：`account` → `account_info` → `friendship` → `friendship_reverse` → `room_info` → `room_member` → `account_room`。

### 4.1 account

```sql
create table account (
    id               bigint      generated by default as identity primary key,
    type             text        not null,
    owner_account_id bigint,
    turms_sync_state text        not null default 'pending',
    created_at       timestamptz not null default now(),
    updated_at       timestamptz not null default now(),
    constraint account_type_chk   check (type in ('human', 'agent')),
    constraint account_sync_chk   check (turms_sync_state in ('pending', 'synced')),
    constraint account_owner_chk  check ((type = 'agent') = (owner_account_id is not null)),
    constraint account_no_self_owner_chk check (owner_account_id is null or owner_account_id <> id)
);

create index account_owner_idx on account (owner_account_id) where owner_account_id is not null;
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `id` | `bigint` | 否 | 主键；身份本体等于 Turms 用户 id，由 Biz 侧 identity 生成 |
| `type` | `text` | 否 | `human` / `agent`，由 check 约束限定 |
| `owner_account_id` | `bigint` | 是 | 逻辑引用 `account.id`；只有 agent 有值且不可转移 |
| `turms_sync_state` | `text` | 否 | `pending` / `synced`；注册或改名后回到 `pending` |
| `created_at` | `timestamptz` | 否 | 创建时间；默认 `now()`，审计用 |
| `updated_at` | `timestamptz` | 否 | 更新时间；由应用写入，不建触发器 |

- **id 起始段**：identity 默认从 1 开始。Turms 内置账号（管理端登录的 `turms` 等）是否占用低 id **未实测**，Turms 打通阶段一并确认；若冲突，只给序列加 `start with`，不改表结构。
- **头像不落库**：按账号 id 生成固定头像（`moonchat-product` §5.3），所以没有 `avatar` 列。
- **冻结的写入口不在 V1 接口清单里**：`account_info.status` 存在是因为 spec 已经假设了「未冻结」这个判据；谁来冻结是平台运维动作，不是产品能力。

### 4.2 account_info

```sql
create table account_info (
    account_id      bigint      primary key,
    display_name    text        not null,
    status          text        not null default 'active',
    email           text,
    credential_hash text        not null,
    created_at      timestamptz not null default now(),
    updated_at      timestamptz not null default now(),
    constraint account_info_name_chk check (length(btrim(display_name)) > 0),
    constraint account_info_status_chk check (status in ('active', 'frozen')),
    constraint account_info_email_uq unique (email),
    constraint account_info_credential_uq unique (credential_hash),
    constraint account_info_email_normalized_chk check (
        email is null or email = lower(btrim(email))
    ),
    constraint account_info_email_shape_chk check (
        email is null or position('@' in email) > 1
    )
);
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `account_id` | `bigint` | 否 | 主键，逻辑引用 `account.id`；每个账号恰好一行 |
| `display_name` | `text` | 否 | 展示用；非空，不参与权限判定 |
| `status` | `text` | 否 | `active` / `frozen`；冻结后停写入和好友申请 |
| `email` | `text` | 是 | 真人必填且唯一，agent 为空；存 trim + 小写后的值 |
| `credential_hash` | `text` | 否 | 唯一；只存密码或 API key 的哈希 |
| `created_at` | `timestamptz` | 否 | 创建时间；默认 `now()`，审计用 |
| `updated_at` | `timestamptz` | 否 | 更新时间；由应用写入，不建触发器 |

- **一个账号只有一条主认证凭据**：真人用 **bcrypt**（Spring Security 的 `BCryptPasswordEncoder`，cost 10 起；上限 72 字节，接口层拦住超长密码），agent 用确定性 HMAC-SHA256 + 服务端 pepper（pepper 来源与轮换方式**未确认**）。
- **类型不重复存**：真人或 agent 由 `account.type` 判断，`account_info` 不再加 `type` 列，避免两处类型不一致。
- **agent 密钥必须可反查**：agent 带着明文密钥来，Biz 算出确定性哈希后按 `unique (credential_hash)` 定位账号；加盐慢哈希做不到这一点，只用于真人密码。
- **哈希格式自带算法标记**：实现时在 `credential_hash` 中使用带方案前缀的编码，例如 `bcrypt$2a$...` 与 `hmac-sha256$...`，以便以后迁移算法（换 Argon2id 不需要改表）。
- **名字改动的同步标记仍在 `account`**：改名时在同一事务写 `account_info.display_name` 并把 `account.turms_sync_state` 置回 `pending`。
- **不做邮箱验证、找回密码或密钥轮换**（`moonchat-product` §5.3、`moonchat-agent-connection`）：没有验证时间、重置令牌或密钥历史列。
- **没有回报地址列**：上一版的 `webhook_url` 已删除。agent 与真人一样用该账号的 Turms 凭据收消息，平台不需要任何入向地址（`moonchat-agent-connection`）。

### 4.3 friendship

```sql
create table friendship (
    id              bigint      generated by default as identity primary key,
    account_id      bigint      not null,
    peer_account_id bigint      not null,
    status          text        not null,
    requested_by    bigint      not null,
    created_at      timestamptz not null default now(),
    updated_at      timestamptz not null default now(),
    deleted_at      timestamptz,
    constraint friendship_status_chk   check (status in ('pending', 'accepted')),
    constraint friendship_order_chk    check (account_id < peer_account_id),
    constraint friendship_requester_chk check (requested_by in (account_id, peer_account_id)),
    constraint friendship_pair_uq      unique (account_id, peer_account_id)
);

create index friendship_deleted_at_idx
    on friendship (deleted_at)
    where deleted_at is not null;
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `id` | `bigint` | 否 | 主键；好友关系的稳定标识，用于申请操作和反向表关联 |
| `account_id` | `bigint` | 否 | 逻辑引用 `account.id`；规范序中放较小的账号 id |
| `peer_account_id` | `bigint` | 否 | 逻辑引用 `account.id`；规范序中放较大的账号 id |
| `status` | `text` | 否 | `pending` / `accepted`；拒绝不增加枚举值，而是写 `deleted_at` |
| `requested_by` | `bigint` | 否 | 逻辑引用 `account.id`；必须是关系双方之一 |
| `created_at` | `timestamptz` | 否 | 创建时间；默认 `now()`，审计用 |
| `updated_at` | `timestamptz` | 否 | 更新时间；由应用写入，不建触发器 |
| `deleted_at` | `timestamptz` | 是 | 空表示有效；非空表示已拒绝或已删好友 |

- **主表是唯一业务真相**：申请、同意、拒绝、软删先由这里确定结果，再在同一事务同步 `friendship_reverse`。
- **`id` 保持稳定**：列表查询仍按账号定位关系，反向表关联使用 `id`；对外的同意、拒绝与删除由 Biz 用 `peer_account_id` 定位到本行（`moonchat-api` §5），不把 `id` 交给客户端。
- **小 id 查主表，授权也查主表**：查询好友列表时按账号在规范序中的位置选择表；判断两人是否好友时一律规范序后读 `friendship`。
- **`requested_by` 用于区分收发申请**：待处理列表必须据此只返回发给当前账号的申请，并在同意或拒绝时校验操作方；该字段不能由两个账号 id 或状态推导。
- **拒绝 = 软删**：状态枚举仍只有 `pending` / `accepted`，拒绝写 `deleted_at`；对方可以再申请，V1 没有冷却期也没有拉黑（拉黑在 V2）。
- **删除后重新申请 = 复用原行**：在 purge 前重新加好友时，清空 `deleted_at`，把状态置回 `pending`，更新 `requested_by` 与时间；不插入第二个同 pair 行。
- **没有 `turms_*` 列**：好友永不投影进 Turms，这类列永远不会有值。
- **删好友不动任何设置**：会话保留、历史只读由 Turms 保证；没有任何投递设置随好友关系删除。

### 4.4 friendship_reverse

```sql
create table friendship_reverse (
    account_id      bigint      not null,
    peer_account_id bigint      not null,
    friendship_id   bigint      not null,
    status          text        not null,
    requested_by    bigint      not null,
    created_at      timestamptz not null default now(),
    updated_at      timestamptz not null default now(),
    deleted_at      timestamptz,
    constraint friendship_reverse_pk           primary key (account_id, peer_account_id),
    constraint friendship_reverse_friendship_uq unique (friendship_id),
    constraint friendship_reverse_status_chk   check (status in ('pending', 'accepted')),
    constraint friendship_reverse_order_chk    check (account_id > peer_account_id),
    constraint friendship_reverse_requester_chk check (requested_by in (account_id, peer_account_id))
);

create index friendship_reverse_deleted_at_idx
    on friendship_reverse (deleted_at)
    where deleted_at is not null;
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `account_id` | `bigint` | 否 | 逻辑引用 `account.id`；反向存储，放较大的账号 id |
| `peer_account_id` | `bigint` | 否 | 逻辑引用 `account.id`；反向存储，放较小的账号 id |
| `friendship_id` | `bigint` | 否 | 逻辑引用 `friendship.id`；唯一，与主表一行对应 |
| `status` | `text` | 否 | `friendship.status` 的镜像，不能独立修改 |
| `requested_by` | `bigint` | 否 | `friendship.requested_by` 的镜像，不能独立修改 |
| `created_at` | `timestamptz` | 否 | `friendship.created_at` 的镜像，默认 `now()` |
| `updated_at` | `timestamptz` | 否 | `friendship.updated_at` 的镜像，不能独立修改 |
| `deleted_at` | `timestamptz` | 是 | `friendship.deleted_at` 的镜像；空表示有效 |

- **这是可重建查询镜像，不是第二份真相**：申请、同意、拒绝、软删和恢复都必须与 `friendship` 在同一事务内同步，一次写入使用同一个应用时间值。
- **只为按较大账号查询**：大 id 查本表，小 id 查 `friendship`；按账号分片后两端都能直接路由。
- **不参与授权**：判断好友关系、处理申请和删除好友都必须以 `friendship` 为准。
- **V1 单库不带来查询性能收益**：代价是每条好友关系写两行；收益是未来按账号分片时不需要跨分片扫描。

### 4.5 room_info

```sql
create table room_info (
    id               bigint      generated by default as identity primary key,
    name             text        not null,
    owner_account_id bigint      not null,
    turms_group_id   bigint,
    turms_sync_state text        not null default 'pending',
    created_at       timestamptz not null default now(),
    updated_at       timestamptz not null default now(),
    constraint room_info_name_chk      check (length(btrim(name)) > 0),
    constraint room_info_sync_chk      check (turms_sync_state in ('pending', 'synced')),
    constraint room_info_turms_group_uq unique (turms_group_id)
);
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `id` | `bigint` | 否 | 主键，也是对外使用的 `room_id` |
| `name` | `text` | 否 | 群名；不能为空，可以重复 |
| `owner_account_id` | `bigint` | 否 | 逻辑引用 `account.id`；群主只有一个 |
| `turms_group_id` | `bigint` | 是 | Turms 群句柄；建群投影成功前为空 |
| `turms_sync_state` | `text` | 否 | `pending` / `synced`；成员或群资料变化后回到 `pending` |
| `created_at` | `timestamptz` | 否 | 创建时间；默认 `now()`，审计用 |
| `updated_at` | `timestamptz` | 否 | 更新时间；由应用写入，不建触发器 |

- **没有 `visibility` 列**：第一版只有一种可见性（成员可见），它由 `moonchat-messaging` 的 `GroupType` 配置表达，不是每个群的一列数据；公开群要等 Turms 只读能力实测（`moonchat-product` §5.3）。
- **没有 `deleted_at`**：V1 的能力清单里没有「解散群」（`moonchat-product` §4.1），群一旦建立就一直存在；可软删的只有成员关系。真要做解散，先改 spec 并实测 Turms 侧删除 group 的行为，再补这一列。

### 4.6 room_member

```sql
create table room_member (
    room_id    bigint      not null,
    account_id bigint      not null,
    joined_at  timestamptz not null default now(),
    deleted_at timestamptz,
    constraint room_member_pk primary key (room_id, account_id)
);

create index room_member_deleted_at_idx
    on room_member (deleted_at)
    where deleted_at is not null;
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `room_id` | `bigint` | 否 | 逻辑引用 `room_info.id`；与 `account_id` 组成主键 |
| `account_id` | `bigint` | 否 | 逻辑引用 `account.id`；与 `room_id` 组成主键 |
| `joined_at` | `timestamptz` | 否 | 最近一次加入时间；默认 `now()`，不参与判定 |
| `deleted_at` | `timestamptz` | 是 | 空表示当前成员；非空表示已退群或被移除 |

- **这是群成员关系的唯一业务真相**：成员列表和“是否群成员”都读本表；`account_room` 不能用于发送授权。
- **没有 `role` 列**：群主就是 `room_info.owner_account_id`，成员表只回答「在不在群里」；也不做成员变更历史。
- **建群是一次事务**：写 `room_info` 一行 + 给群主写 `room_member`、`account_room` 各一行，然后才投影；「群主一定是成员」是事务产物。
- **退群 / 被移除 = 同步写 `deleted_at`**：没有独立 `left_at`；「重进群只看到增量」不需要历史。
- **重新进群 = 复用原行**：在 purge 前重新进群时清空 `deleted_at`，把 `joined_at` 更新为本次加入时间，不插入第二个同 pair 行。
- **Turms 投影只读本表**：投影按 full reconcile 整组重算（`moonchat-messaging`）。

### 4.7 account_room

```sql
create table account_room (
    account_id bigint      not null,
    room_id    bigint      not null,
    joined_at  timestamptz not null default now(),
    deleted_at timestamptz,
    constraint account_room_pk primary key (account_id, room_id)
);

create index account_room_deleted_at_idx
    on account_room (deleted_at)
    where deleted_at is not null;
```

| 列 | 类型 | 是否可空 | 规则 |
| --- | --- | --- | --- |
| `account_id` | `bigint` | 否 | 逻辑引用 `account.id`；与 `room_id` 组成反向主键 |
| `room_id` | `bigint` | 否 | 逻辑引用 `room_info.id`；与 `account_id` 组成反向主键 |
| `joined_at` | `timestamptz` | 否 | `room_member.joined_at` 的镜像，不能独立修改 |
| `deleted_at` | `timestamptz` | 是 | `room_member.deleted_at` 的镜像；空表示有效成员 |

- **这是可重建查询镜像，不是第二份真相**：建群、拉人、退群、移除、软删和恢复都必须与 `room_member` 在同一事务内同步，一次写入使用同一个应用时间值。
- **只为按账号查询**：某账号加入的群列表读本表；成员列表和发送授权读 `room_member`。
- **不参与 Turms 投影**：`room_info.turms_sync_state` 的重算只读取 `room_member`。
- **V1 单库不带来查询性能收益**：代价是每条成员关系写两行；收益是未来按群、按账号分片时两端都能直接路由。

## 5. 只能由应用层守的规则

数据库是最后兜底，不是全部规则。下面这些约束表达不了，落在 Biz 的领域层，实现时逐条对应到代码：

| 规则 | 依据 | 为什么不在 DB |
| --- | --- | --- |
| 所有引用列写入时必须指向仍存在的业务行；删除父行时先删不再需要的子行 | 本文 §3 的「所有外键都是逻辑外键」 | DDL 不建物理外键，引用完整性由应用层事务保证 |
| 每个账号恰好有一条 `account_info`；真人必须有 `email`，agent 必须没有 `email` | `moonchat-accounts`、`moonchat-product` §5.1 | 需要联表读取 `account.type`，单表 check 无法判断 |
| `friendship_reverse` 必须与 `friendship` 的关系 id、两人、状态、申请人、时间和 `deleted_at` 完全一致 | `moonchat-friends` | 跨表行级镜像，PG 无法用单行约束表达；由 Biz 在同一事务内双写 |
| `account_room` 必须与 `room_member` 的群、账号、加入时间和 `deleted_at` 完全一致 | `moonchat-messaging` | 跨表行级镜像，PG 无法用单行约束表达；由 Biz 在同一事务内双写 |
| 好友与群成员的所有业务查询、授权判断都必须排除 `deleted_at is not null` 的行 | `moonchat-friends`、`moonchat-messaging` | tombstone 仍是普通行，数据库无法替所有查询自动过滤 |
| 软删、恢复和 tombstone purge 必须同步处理主表与反向表 | 本文 §3 | 两张表共享一个关系生命周期，PG 无法用单行约束表达 |
| 归属者必须是真人账号 | `moonchat-accounts` | 跨行类型判断，PG 的 check 做不到；为一条规则加触发器不划算 |
| 建群时给群主写 `room_member`、`account_room` 各一行 | `moonchat-product` §4.1 | 事务内的跨表写入，不是单行约束 |
| 群主不能被移除、也不能退群：`owner_account_id` 永远指向一个有效成员 | `moonchat-messaging` | 跨表不变量，单行 check 表达不了 |
| `dm` 的对端必须是已成立的好友 | `moonchat-friends`、`moonchat-messaging` | 这是决策时点的授权判断，不是存储约束；好友被删后旧行仍在是正常状态 |
| `room` 会话要求调用方是 `room_member` | `moonchat-messaging` | 同上，属于授权事实判断 |
| 写入网关的 `senderId` 必须来自入口凭据，不允许代他人发言 | `moonchat-messaging`、`moonchat-agent-connection` | 这是认证结果向写入路径的传递，不是存储约束 |
| 名字、邮箱与密码的长度规则 | 名字 ≤ 20（Turms 默认）、邮箱 ≤ 254（RFC 上限）、密码 8..72 且不能纯数字（72 是 bcrypt 硬上限） | 名字来自 Turms；邮箱与密码是我们自己定的（腾讯系卡在 16 位且不能纯数字，我们更宽松） |
| 冻结账号停写入、停好友申请 | `moonchat-agent-connection`、`moonchat-friends` | 读 `account_info.status` 的是写入网关与好友接口，不在写库路径上 |

**一条硬底线**：上表任何一条都**不许**用「顺手加个表、加个缓存」来实现。授权事实一律现查 PG，因为「业务真相只在 PG」是整套设计的支点。

## 6. 明确不建的表与列

| 不建 | 理由 | 真相在哪 |
| --- | --- | --- |
| 消息、会话 | 消息只由隧道写，PG 一行副本都没有 | Turms（MongoDB） |
| `workspace` 表或 `workspace_id` 列 | 工作区这个概念已删除：agent 就是它账号的一个客户端 | 不存在 |
| `conversation_setting` 表、推送档位 | 平台没有投递设置：agent 收它账号的全部会话，自己筛 | 不存在 |
| 限流桶（账号 → 会话两级） | 可重建的运行状态，不是业务真相；重启归零不影响正确性 | Biz 的 Redis 键空间 |
| 来源标记、限流命中、审计表 | V1 只打结构化日志，不建可查询审计 | 日志（`moonchat-product` §5.3） |
| 授权表、角色权限表、agent 用户映射表 | 身份只有一处真相：`account.id` 就是 Turms 用户 id，归属关系本身就是授权 | `account` |
| Turms group / member 的本地副本 | 它们是可重建投影，再存一份就是第二个真相 | 投影源是 `room_info` / `room_member` |
| 好友申请单独一张表 | 申请与成立只是同一行的两个状态 | `friendship.status` |
| 拉黑、举报、备注、分组、亲密度 | 范围问题，不是表结构问题 | 不做 |
| 邮箱验证、找回密码、密钥轮换 | 已定的简化，对应能力不存在 | 不做 |
| `version`、通用审计列 | 关系表与成员表只需要 `deleted_at` tombstone，不需要通用版本或审计 | 不需要 |

## 7. 每张表的出处

| 表 | spec 依据 | 关键句 |
| --- | --- | --- |
| `account` | `moonchat-accounts` | 「一张 `account` 表，`type ∈ {human, agent}`；agent 账号带 `owner_account_id`」 |
| `account_info` | `moonchat-accounts`、`moonchat-product` §5.1 | 账号名字、状态与统一认证哈希；真人邮箱密码，agent 用确定性密钥哈希 |
| `friendship`、`friendship_reverse` | `moonchat-friends`（`id`、规范序、`requested_by`）；反向表为本次表结构决策 | 好友主从镜像：`friendship` 是唯一真相，反向表按账号查询 |
| `room_info`、`room_member`、`account_room` | `moonchat-messaging`（群与成员投影、`turms_group_id` 回填）；反向表与软删为本次表结构决策 | 群信息与群成员主从镜像：`room_member` 是唯一真相，反向表按账号查询 |

## 8. 待确认

三项已经清掉（源码核对结果）：Admin API 能用指定 id 建用户，但**建群不能指定 id**（`AddGroupDTO` 没有 id）→ `turms_group_id` 必定由 Turms 生成后回填；`POST /messages` 能带 `senderId` 代发；Turms 默认的名字上限 20、正文上限 500 已进入接口约束。细节在 `moonchat-messaging` 的「要核对的 7 条」。

| 事项 | 现状 | 卡在哪 |

| 索引是否够用 | 除主键、唯一约束和四个 `deleted_at` purge 索引外，只建 `account_owner_idx`；好友与群成员的有效行查询命中主表与反向表主键 | V1 单实例没有实测数据，等真实流量再补，不预建 |
